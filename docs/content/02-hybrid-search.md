# 기술 블로그 2편: 벡터 검색에 RRF와 reranker를 추가한 이유

## 벡터 검색만으로 부족했던 지점

의미가 비슷한 문장을 찾는 데 임베딩은 강하지만, 사내 문서에는 제도명·약어·정확한 숫자처럼 문자열 일치가 중요한 정보가 많다. 예를 들어 “법인카드 영수증 제출 기한”이라는 질문에서 `법인카드`, `영수증`이 정확히 함께 등장하는 청크는 키워드 신호가 강하다.

이 프로젝트는 pgvector cosine 검색과 `pg_trgm` similarity 검색에서 각각 상위 20개를 가져온다. 두 점수는 의미와 범위가 달라 정규화 후 가중합하는 대신 RRF를 사용한다.

## RRF 결합

각 검색기의 청크 순위를 `rank`라 할 때 RRF 점수는 다음과 같다.

```text
RRF(d) = Σ 1 / (k + rank(d))
```

기본 `k=60`으로 두 검색기에 모두 등장한 결과를 자연스럽게 올린다. 같은 검색기에서 중복된 청크는 한 번만 계산한다. 원점수 분포가 달라져도 순위 결합 규칙은 유지된다.

관련 구현 기록:

- `81630c1`: 병렬 벡터·키워드 검색, RRF, cross-encoder reranker
- `ced8506`: Recall@K·MRR·nDCG@K 평가 도구와 추적

## reranker 비용을 제한하는 방법

cross-encoder는 질문과 각 청크를 함께 읽어 관련도를 다시 계산하므로 임베딩 검색보다 정확하지만 느리다. RRF 상위 12개만 `BAAI/bge-reranker-v2-m3`에 전달하고 최종 5개만 답변 근거로 사용한다. 모델은 첫 요청에 lazy loading하며 API 이벤트 루프를 막지 않도록 별도 스레드에서 추론한다.

## 재현 가능한 평가

평가 데이터는 질문과 관련 청크 ID를 JSONL로 고정한다. 각 검색 방식에서 반환한 청크 ID를 같은 질문 순서로 저장하고 다음 지표를 계산한다.

- Recall@5: 관련 청크 중 상위 5개가 찾은 비율
- MRR: 첫 관련 청크 순위의 역수 평균
- nDCG@5: 관련 청크가 상위에 배치된 정도

```powershell
python -m evaluation.run --results evaluation/retrieval-results.example.jsonl
```

저장소의 예제 결과는 평가기 동작을 검증하기 위한 합성 fixture이며 모델 성능 주장이 아니다. 실제 블로그에 수치를 게시할 때는 문서 버전, 질문 수, 모델명, 청크 설정, 측정 시각을 함께 기록해야 한다.

## 답변 출처의 신뢰 경계

LLM 프롬프트에는 `[출처 N] 파일명, p.N` 형식으로 근거를 넣지만, API의 구조화된 `sources`는 모델 출력에서 추출하지 않는다. 검색 결과가 가진 문서·페이지 메타데이터로 별도 생성한다. 모델이 잘못된 출처 번호를 쓰더라도 클라이언트는 신뢰 가능한 원본 위치를 받을 수 있다.
