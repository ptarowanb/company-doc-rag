# 기술 블로그 1편: 사내 문서 RAG를 모듈형 백엔드로 설계한 이유

## 글의 목적

“PDF를 벡터 DB에 넣고 LLM에 전달했다”에서 끝나지 않고, 실제 백엔드 서비스에서 필요한 비동기 처리·실패 복구·출처 신뢰성·재현 환경까지 설계한 과정을 설명한다.

## 문제 정의

사내 규정은 파일 단위로 흩어져 있고 사용자는 정확한 문서명보다 자연어 질문으로 정보를 찾는다. 단순 키워드 검색은 표현이 달라지면 놓치고, 벡터 검색만 사용하면 문서에 정확히 등장하는 제도명이나 숫자의 우선순위가 낮아질 수 있다. 생성 모델만 호출하면 근거 없는 답변과 출처 조작 위험도 남는다.

이 프로젝트의 성공 기준을 다음처럼 정했다.

- PDF 업로드 요청은 오래 기다리지 않고 작업 ID를 반환한다.
- 페이지 메타데이터가 파싱부터 답변 출처까지 유지된다.
- 벡터·키워드·reranker 단계를 분리해 품질을 비교할 수 있다.
- 외부 API 없이 대부분의 테스트를 반복 실행할 수 있다.
- Docker Compose 한 명령으로 로컬 환경을 재현한다.
- 운영 환경은 AWS Terraform으로 매핑하되 실제 비용은 발생시키지 않는다.

## 왜 모듈형 모놀리스인가

수집·검색·답변을 각각 마이크로서비스로 나누면 독립 확장은 쉽지만, 초기 포트폴리오에서 배포와 메시지 계약 복잡도가 RAG 품질 실험보다 커진다. 반대로 모든 코드를 FastAPI 라우터에 넣으면 작업자 분리와 테스트 대역 교체가 어려워진다.

그래서 하나의 Python 패키지 안에서 `domain → application → infrastructure/api` 방향으로 의존성을 제한하고 API와 Celery worker만 프로세스로 분리했다. 같은 모델과 유스케이스를 공유하면서도 PDF 처리가 요청 스레드를 점유하지 않는다.

- `e4ce01b`: 페이지 보존 PDF 파싱·청킹
- `68cdd14`: PostgreSQL/pgvector 저장 계층
- `fecd6e7`: 비동기 문서 API·Celery·Redis

## 데이터 흐름에서 지킨 불변 조건

문서 ID와 SHA-256은 중복 처리와 멱등성의 기준이다. `READY` 문서는 다시 임베딩하지 않고, 오류는 `FAILED`와 안전한 오류 코드로 남긴다. 청크에는 파일명 대신 문서 ID, 페이지 시작·끝, 토큰 수를 저장한다. 답변 출처는 LLM 문자열을 파싱하지 않고 검색 결과에서 직접 만든다.

이 경계를 두면 공급자 SDK를 바꾸더라도 도메인 모델과 API 응답 계약을 유지할 수 있다. 기본 테스트에서는 가짜 임베더와 생성기를 주입해 과금과 네트워크 변동도 제거했다.

## 로컬 재현과 다음 실험

`docker compose up --build`는 API, worker, pgvector, Redis를 시작한다. 첫 번째 후속 실험은 청크 크기와 겹침 비율 변화가 Recall@5와 답변 첫 토큰 시간에 미치는 영향을 비교하는 것이다. 두 번째 글에서는 벡터 검색 단독과 하이브리드·reranker 조합을 같은 질문 세트로 평가한다.
